# Four Nights at the Burger Shop Numeric Modifier

A stats mod for *Four Nights at the Burger Shop ～ハンバーガー食べながら食べられるミニゲーム～*.

**The game itself is never modified.** The game ships as a Unity 2022.1.24f1 (Mono) build, and all of its logic lives in
`Four Nights at the Burger Shop_Data\Managed\Assembly-CSharp.dll`. The mod takes the BepInEx plugin route: while the game runs
it uses reflection to read and write the numeric fields in memory, and not a single byte of `Assembly-CSharp.dll` is touched.
Uninstall it once and the game is back to stock immediately.

---

## 1. Installing (the installer is recommended)

Double-click **`汉堡店修改器-安装程序.exe`**:

1. It locates the game folder by itself (first the folder it is sitting in, then the standard folder name on each drive, then the registry).
   If it cannot find one, click "Browse…" and pick the folder by hand; the folder you pick must contain `Four Nights at the Burger Shop.exe`.
2. Click **Install**. It refuses to install while the game is running (`winhttp.dll` would be locked).
3. To start playing right after installing, tick "Launch the game when done" in the bottom-left corner.

**Uninstalling**: click "Uninstall and restore" in the same program, or run the bundled `卸载还原.ps1`.
Uninstall removes exactly what the manifest written at install time lists, and **files that existed before the install are never touched** —
so an existing BepInEx environment of your own will not be deleted by mistake.

**Silent install / uninstall from the command line** (for scripts):

```powershell
汉堡店修改器-安装程序.exe --install   "D:\...\Four Nights at the Burger Shop ..."
汉堡店修改器-安装程序.exe --uninstall "D:\...\Four Nights at the Burger Shop ..."
```

With no directory argument it locates the game by itself. If a file is held by the system during uninstall (the game was just running),
it is registered as **delete on next reboot** and the console tells you so.

The panel shows live values: current HP, ecstasy, resistance, burgers in a row, the day's progress and the time of day.

> **Hotkeys**: `F9` toggles the panel | `F5` (or `F6`) forensic snapshot | `F7` full robustness self-test |

>

> steadier route (F6 may be taken by the system, which is why the snapshot is bound to F5 as well). Everything they produce goes into
> `BepInEx\l2d_dump\`; you can ignore it during normal play.

## 4. What you can change

The panel is **tabbed** (Player / Fellatio / Rear / Riding / Outfit / System / Presets / About), can be "collapsed", and its content area scrolls.
Every value has **"−" and "+" step buttons** — use them for fine adjustment when the slider is too coarse.

### Change rates (the core feature: scales the amount of each actual change)

| Rate | 100% (default) | Effect at 0% |
| --- | --- | --- |
| **HP loss rate** | vanilla damage | **HP never drops** |
| **HP recovery rate** | vanilla healing | eating a burger heals nothing |
| **Ecstasy gain rate** | vanilla accumulation | **ecstasy never increases at all** (equivalent to not being absorbed) |
| **Ecstasy decay rate** | vanilla decay | ecstasy does not decay |

Above 100% the change is amplified (200% = double damage, for example).
The implementation is **Harmony prefix patches** hooked onto `PlayerControl.HPChange` / `EcstasyChange` /
`ECstasyReset` / `HPGaugeChangeValue` / `EcstasyGaugeChangePercent`,
**scaling the arguments before the method body runs** — so the game's own events and the HP-bar UI stay consistent; nothing is forced after the fact.

### Cap countermeasures (game mechanic: being Drained permanently shaves your caps)

How the game actually works:

```
Drained → HPGaugeChangePercent(-3~5%)    → maxHP drops step by step
        → EcstasyGaugeChangePercent(-1~5%) → maxEcstasy drops step by step
Eat a burger → heal = maxHP × 回復量%    ← healing is a percentage of the cap
DLC on and overflowing → HPGaugeChangePercent(+) → only then does the cap rise again
```

So once the caps have been shaved, **healing gets harder and harder**. The countermeasures:

| Item | Description |
| --- | --- |
| **Lock HP cap / lock ecstasy cap** | when a cap is shaved, press it straight back to the baseline (the field is written exactly, with no percentage compensation, to avoid cumulative drift) |
| **HP / ecstasy cap target** | an **absolute value** target, approached smoothly every frame at the "approach speed"; 0 = disabled |
| **Approach speed** | points per second; lower is smoother |
| **×1.5 / ×2 / restore default** | quick target presets |

> **Why "set it to a value" rather than "add a percentage"**: an early version worked in percentages and multiplied once per slider
> change, so dragging **expanded exponentially** into the hundreds of thousands or tens of millions and caused stutter. Now the slider
> only sets a target and every frame approaches it under control, which rules that out at the root.
> There is also a **hard cap guard at 20000**; anything above it is pushed back.

### Player

| Item | Description |
| --- | --- |
| **Invincible (HP refilled every frame)** | goes through the game's own `HPChange`, so the bar follows; note that it **does not stop the cap from dropping** (use the countermeasures above for caps) |
| **Zero ecstasy** | cleared every frame, so the other side cannot put you into the ejaculation state |
| **Ecstasy resistance 0–1** | goes through the game's own resistance field; 1 = full immunity; vanilla only maxes it out temporarily while R is held |
| **HP / ecstasy cap target** | **controls the cap only** (`maxHP` / `maxEcstasy`) and never the current value — see "About ecstasy" below |
| **Max burgers in a row** | vanilla 10, i.e. `maxBurgerNum` (**written once when the slider changes**; it does not pin the game's own value down every frame) |
| **Ejaculation count** | `syaseiCount`, same as above (a change takes effect when you make it, then the game goes back to incrementing it) |
| **Reset burger layers** | see below |

### About ecstasy: why it sometimes "maxes out instantly" or "never moves at all"

These two extremes come from the interaction between two of the game's own calculation rules and the mod's settings; **they are not random bugs**:

```csharp
// PlayerControl.EcstasyChange(float amount)
CurrentEcstasy += amount * (1f - EcstasyResist);              // (1) the delta is scaled by resistance
CurrentEcstasy = Mathf.Clamp(CurrentEcstasy, 0f, maxEcstasy);  // (2) hard-clamped to the cap
```

| Symptom | Mechanism |
| --- | --- |
| **Maxes out instantly** | one version **filled the current value to 99% every frame** whenever the cap target was above 0, wiping out everything the player did. **That behaviour has been removed**; the cap target now **only controls `maxEcstasy`** and never touches the current value |
| **Never moves at all** | resistance in (1) pulled to **1** → `amount × 0 = 0`, so no delta gets through; or **"zero ecstasy"** is on (cleared every frame). Both are intentional switches, but together they freeze the value completely |

So read these three panel items together:

- **Ecstasy cap target** (say 200) → sets the cap only; that value approaches smoothly and the current value grows as it should
- **Zero ecstasy** → turn it on only when you want "not to be absorbed"; while it is on the value never moves
- **Ecstasy resistance** → `0` = normal resistance applies, `1` = full immunity; once it is at 1 the value never moves

> A related note: ecstasy **really cannot be filled to the top**. As soon as `Update_Syasei()` decides
> `CurrentEcstasy >= maxEcstasy` it sets `Syaseing = true`, and while `Syaseing` is true `EcstasyChange`
> ignores positive deltas for the whole call — the value stops changing and the character's motion stops too.
> The right move is **not to fill it at all**: let the player play to the top, rather than "filling it to 99% on the player's behalf".

### Ecstasy tremor and ecstasy adaptation

An optional mechanic (on by default). **Trigger**: every time ecstasy **accumulates**, a chance (22% by default) starts one oscillation.

**The process**: the oscillation is a decaying sine whose **centre line is itself steadily falling** — it does not "wobble around a fixed value";
it carries the ecstasy value downward and finally stops at

```
landing point = v1 − this gain × loss%
```

The landing loss is 85% by default and **may exceed 100%** — then the landing point is pressed **below the value from before the oscillation**,
so the wobble not only erases this gain but eats into what was already there. That is exactly where the feeling of "adaptation" comes from.

**Steadying**: pressing `R` (the game's own resist key) during the **first half** of the oscillation cuts the loss from 85% to 8%, keeping almost all of it.
Steadying repeatedly builds up a feel counter.

**Slowdown templates (each of a different length)**: during an oscillation the character's motion slows down, and the speed is not one fixed value — it undulates according to the chosen template:

| Template | Period | Shape |
| --- | --- | --- |
| **Jolt** | 0.42s | a short square wave — reads as a stutter when the attack rate is high |
| **Spasm** | 0.30s | high-frequency fine shaking — small amplitude, but always trembling |
| **Sink** | 2.20s | long and deep — all the way down once, stays a while, then slowly returns |
| **Hesitation** | 1.40s | two hesitations — starts to move, then shrinks back |
| **Tide** | 0.90s | smooth rise and fall |

You can pin a template, or set `0` to pick one at random each time.

**Resonance**: ecstasy accumulates in pulses tied to the **character's attack animation** (every accumulation call site is in the side-position girl's attack code),
so the faster the attack rate, the denser the pulses. With resonance on, **the oscillation frequency follows the attack pulses** — a fast attack rate gives finer, quicker trembling, a slow one gives heavier, deeper swells.

**Ecstasy adaptation (after the oscillation ends)**: it lasts a while, during which

- later ecstasy accumulation is cut to a given multiplier (35% by default)
- **on the health side**: a higher cap (+20% by default), reduced damage (you take only 35% of it by default), and regeneration per second (6% of the cap by default)

Combined with the "ecstasy decay rate", this produces a net decrease: **the reduction holds accumulation down while the game's natural decay keeps running,
and the difference between the two is a net drop** — with a high decay rate the ecstasy value keeps sinking.

> **Two hard constraints (both learned the hard way; do not touch them when changing the code)**
>
> 1. **No buff is permanent**: a health-cap bonus is booked as a **delta**, and the same number is subtracted when it ends,
>    rather than writing back a snapshot (the snapshot may already be stale, and writing it back corrupts the value for good).
>    And **settle the previous round before adding a new one** — otherwise the new round stacks on a cap that already includes the bonus,
>    round after round (measured to run away).
> 2. **The safety valve**: once ecstasy reaches 90% of the cap, tremor and adaptation **stop reducing** accumulation.
>    This valve must not be removed — if ecstasy can never reach the cap, `Update_Syasei()` never sets `Syaseing`,
>    and the Drain loop never terminates.

### Logic cross-check (a debugging tool)

The mod hands `maxHP / maxEcstasy / timeScale / bar size` to **seven independent per-frame writers**
(`KeepMaxCaps`, `PumpCaps`, the circuit breaker, `SetMaxExact`, `RaiseMaxHp`, the tremor's health bonus, the adaptation restore).
None of them owns the value and none of them has a turn order — **so every new mechanic may fight with one of them**.

This tool writes down "the relationships they are supposed to satisfy" explicitly and checks them one by one, turning contradictions into a readable
report instead of waiting for them to show up as strange gameplay.

```bash
bash tools/gcmd.sh xcheck        # one full check → cmd/xcheck.txt
bash tools/gcmd.sh "xwatch 900"  # watch continuously for 15 minutes, once per second, logging only anomalies → cmd/xwatch.txt
```

**The 16 invariants**:

| # | Check | What failing it means |
| --- | --- | --- |
| (1) | Cap ceiling (3000) | a writer is running away |
| (2) | Health-bonus bookkeeping balances | a bonus was never settled, or was settled twice |
| (3) | Ecstasy reachability safety valve | the Drain may never terminate |
| (4) | Ecstasy value range | the value is out of bounds |
| (5) | `Syaseing` consistent with the value | the Drain state is stuck |
| (6) | The three suppression flags are reset | some code path left one set |
| (7) | Time scale matches expectation | the slowdown template is computed wrong |
| (8) | Tremor state consistent | the tremor state machine is wrong |
| (9) | Bar size vs. baseline | **the bar has been stretched or shrunk** |
| (10) | Ecstasy gain rate not zeroed | ecstasy never grows |
| (11) | Ecstasy not fully frozen | resistance plus zeroing nails the value down |
| (12) | Drain not looping | Drain replays over and over |
| (13) | Cap not shaved too small | fuel for the Drain spiral |
| (14) | Time scale not zeroed | **animation stops → animation events never fire → `Syaseing` is never cleared** |

> **A real case found by check (9)**: the bar had been stretched to **exactly twice** the baseline (`642.8 → 1285.6`).
> The cause is that the bar's length in the game is **event-driven multiplicative accumulation**:
> `HPGauge_Current.sizeDelta = new Vector2(x + x * percent/100f, y)` —
> every `GaugeChangePercent` multiplies the **current width** again.
> The mod changes caps through two paths, `RaiseMaxHp` and `SetMaxExact`, so one change was reported twice → +100% accumulated.
> The fix is **to pin the bar size back to the baseline every frame** (the bar's actual fill is `fillAmount`, independent of size, so pinning the size does not affect the displayed health).

> **Where check (14) came from**: every place that clears `Syaseing` is an **animation event**
> (`Event_FellaSyaseiOnEnd` / `Event_SitSyasei_OnEnd` / `Event_SitKissSyaseiOnEnd` / `Event_OsiriSyaseiOnEnd`).
> So **zeroing the time scale = making Drain never terminate**. The `timescale` command now has a 0.05 floor.

> **Checks (15) and (16)**: (15) asks whether an effect is firing over and over (the Drain red flash comes from `Play吸精Effect`,
> the damage red flash from `PlayEsctasyDamageEffect`); (16) asks whether the current value has gone above the cap
> (the usual source is **locking the cap**, which pins it back to the baseline every frame and fights the Drain's cap shaving).

### Why the "absorb rate" setting does nothing — the game's own integer-division bug

In the game, `Live2D_AnimationControl` has:

```csharp
public int KyuseiRate = 50;          // the "II. Absorb → rate" setting in the options screen

// when an absorb finishes:
else if (UnityEngine.Random.value < (float)(KyuseiRate / 100))
//                                     ↑ int / int = [integer division]
```

`KyuseiRate / 100` is integer division, so the setting is broken:

| What you enter | `KyuseiRate / 100` | Actual effect |
| --- | --- | --- |
| **1 – 99** | **0** | `Random.value < 0` is always false → **never chains; the setting does nothing** |
| **100** | **1** | `Random.value < 1` is **always true** → **endless chain drain** |

**Entering 100 turns Drain into a loop that never ends**: one red flash per round and `Syaseing` is never cleared,
and the game has **8 places** that branch on `if (player.Syaseing)` —
so **a large number of state transitions are blocked** (it looks like "changing state does nothing"). Switching pose resets it because that path bypasses those checks.

**How the mod fixes it**: instead of rewriting the expression, it **borrows** that integer division —
the prefix rolls a die at the **real probability**, then temporarily sets the field to whatever value triggers the intended branch
(true → `100`: `100/100=1` → take "one more round"; false → `99`: `99/100=0` → take the ending), and the postfix restores it unconditionally.
**That is why "rate 50" is really 50%.**

There is also `KyuseiMaxChain` (default 6) as a backstop — after the fix, 100% really means 100% replay,
which would still chain-drain endlessly and lock the game up, so the number of chained drains is capped. **This is a backstop the corrected behaviour needs, not a patch for the original bug.**

> There are only two decision points (grepping `KyuseiRate` across the whole codebase finds it in exactly these two expressions):
> `Event_Fella吸精End` and `Event_FellaSyaseiOnEnd`.
> `Event_Osiri吸精End` and `Even_SitKiss吸精OnEnd` (misspelled in the game — it is missing a t) **do not read** `KyuseiRate`.

### "Cannot get out of the rear riding position" is not a bug, it is the mechanic

```csharp
// the game's click branch:
case "HitArea_Osiri":
    if (tableCol.mouseIsPointingTable) { hitAreaDown = ""; }   // mouse over the table → this click is dropped
    else                               { tabemi.Osiri叩かれる(); }
    break;

// and inside Osiri叩かれる():
if (osiriState == OsiriState.attacking)
{
    Osiri叩く量++;
    if (Osiri叩く量 >= Osiri解除叩く量) Osiri解除();
}
if (osiriState == OsiriState.kyusei || osiriState == OsiriState.syasei)
{
    clickEffect.頭叩くエフェクトガード();      // ← only plays the "blocked" effect, [does not count at all]
}
```

Once you are in the rear riding position (`Osiri`) **she keeps attacking you** (the red flash is the hit effect of each attack),
and **you must click her `Osiri解除叩く量` times (7 by default) to get out**. Until then, "the red never stops and nothing moves" is **the normal mechanic**.

**Two details you have to know (otherwise clicking looks broken):**

| Detail | Description |
| --- | --- |
| **Only clickable during the `attacking` phase** | while she is in the `kyusei` (absorb) or `syasei` (ecstasy) phase, clicks **deliberately do not count**; only a "blocked" effect plays. Wait until she switches back to `attacking` and click then |
| **`Osiri解除叩く量 *= 1.5`** | every escape inside `Osiri解除()` multiplies the required count by 1.5: 7 → 10.5 → 15.75 → 23.6… **the later it gets, the harder it is** |

Also, if `tableCol.mouseIsPointingTable` is true (the mouse is over the **table** collider), the click is dropped outright.

The `states` command reads this state directly, so you do not have to guess:

```bash
bash tools/gcmd.sh states
# 状态机: centerGirlState=Osiri osiriState=attacking Osiri叩く量=0/7 ...
# 点击归属: mouseIsPointingTable=假
```

### Three copies, one per pose: each tab is independent

**The same parameter has its own copy in each of the three tabs**, and changing one **does not** affect the other two.

The config keys carry a suffix:

```
DemandAttBonus_Fella    ← the Fellatio copy
DemandAttBonus_Osiri    ← the Rear copy
DemandAttBonus_Sit      ← the Riding copy
```

**A panel slider applies to "the tab you are looking at"** — go adjust the Fellatio tab while in the rear riding position and you are editing the `_Fella` copy.

> **A pitfall in the implementation (we fell into it)**: the `PIdx` accessor that "picks the current copy" needs a **different index for the game logic and for the panel** —
> the logic needs the **actual pose**, the panel needs the **tab being displayed**.
> Without that distinction the panel looks like it works while editing the wrong object, and **nothing ever reports an error**.

### Trigger chain: from "one smack" to "one stack"

```
one spank (or one click on the head in the seated pose / one attack in Fellatio)
  ├─ (1) speed impulse   : the attack animation rate jumps up for a moment, then slowly decays
  ├─ (2) urge gain       : each time adds a random DemandUrgeMin ~ Max
  ├─ (3) escape penalty  : a DemandEscapePenaltyChance% chance to multiply the clicks needed to escape
  └─ (4) stack check     : see below
```

**The stack check** (`TryStackNow`, **shared by every accumulation source**):

```
urge needed for stack N = DemandThresholdBase + DemandThresholdStep × (N-1)
```

**Two modes** (`DemandTriggerMode`):

| Mode | Behaviour |
| --- | --- |
| **0 — probability mode** | past the threshold, the urge value is still used as a probability and a die is rolled |
| **1 — threshold mode** | reaching the threshold **always** stacks; the urge becomes a plain progress bar (predictable) |

> **All sliders cap at 300%**. The demand urge itself has **no hard cap** — it resets to zero on a stack, which limits it on its own.

**What the accumulation sources are** (all of them feed the stack check):

| Source | Parameters |
| --- | --- |
| Spank / seated click | `DemandUrgeMin` ~ `Max` |
| **Character attack** (rear riding / seated / Fellatio) | `AttackUrgeChance` / `AttackUrgeGain` / `AttackUrgeJitter` |
| **Ejaculation** | `SyaseiUrgeChance` / `SyaseiUrgeGain` |
| **Absorb · chain drain** (afterglow rides the same chain) | `KyuseiUrgeChance` / `KyuseiUrgeGain` |

> **Every slider is a mean value.** Each probability and each gain draws its own factor `1 + U(-j, +j)`
> (`j` = `AttackUrgeJitter`), whose **expected value is exactly 1**, so the long-run average equals the slider value exactly.

**Once all stacks are filled**: no more stacks are added, but **meeting the condition refreshes the duration**
(`DemandMaxStackRefreshMul`, default 100% = adds one full segment; 0 = the original behaviour, nothing happens).

### Effects while Demand / Drain mode is active

| Effect | Parameter | Notes |
| --- | --- | --- |
| Duration | `DemandDurationMin` ~ `Max` | Randomised per segment |
| Maximum segments | `DemandMaxStacks` | Re-triggering while already in the mode **only stacks the total duration** |
| Attack power boost | `DemandAttBonus` | Attack power is `TabemiAtt`, recomputed every frame by `Update`, so this must be hooked as a **postfix** |
| Attack power varies with speed | `DemandAttSpeedBonus` / `Ref` / `Exp` | See below |
| Ecstasy animation rate multiplier | `DemandAnimSpeed` | See below |
| Per-stage acceleration | `DemandSpeedSplit` | On (default): the attack stage uses the game's own `osiriSpeed`, the ecstasy / absorption stage uses the animation multiplier, and **the two do not stack** |
| Block the return to fellatio | `DemandBlockFella` | Cuts out the 10% exit branch |
| Cannot be interrupted | — | Even with full player input it cannot be escaped; only the character ends it, when the timer runs out |

#### The attack-vs-speed curve is a "mild exponential"

The driven quantity is the **actual attack animation rate** (the one the spank impulse pushes up) —
`osiriSpeed` cannot be used: `Play_OsiriMainMixer` pins it at 1, so there is no variation to work with.

```
f = (e^(k·over) − 1) / (e^(k·refv) − 1)      k = DemandAttSpeedExp，0 = 线性
```

**It is normalised**, so the threshold for "full bonus" matches the linear version; only the shape becomes convex:

| k | over=0.10 | 0.25 | 0.40 | 0.50 (full) |
| --- | --- | --- | --- | --- |
| 0 (linear) | 20.0% | 50.0% | 80.0% | 100% |
| **2 (default)** | 12.9% | 37.8% | 71.3% | 100% |
| 4 | 7.7% | 26.9% | 61.9% | 100% |

#### Why the ecstasy animation rate needs its own handling

```csharp
// 游戏原码
if (OsiriMixer.State.IsPlaying) OsiriMixer.State.Parameter = osiriSpeed;
```

`osiriSpeed` **is only applied while the main mixer is playing**. But the ecstasy sequence goes through
`_CenterGirlLayer.Play(OsiriSyaseis[num])`, which **replaces the main mixer** → `IsPlaying` turns false →
`osiriSpeed` has nowhere to go → the ecstasy animation plays at its default speed.

So the speed has to be set directly on **the animation state that is actually playing** (Animancer's `EffectiveSpeed`).

> **The test used is "is the main mixer playing"**, not the stage name in `osiriState`.
> Using the stage name leaves a gap at the instant of the "ecstasy → absorption" switch.
> And the attack animation and the ecstasy animation **share the same layer**, `_CenterGirlLayer == aniA.Layers[0]`,
> so setting the speed every frame without that distinction would **also change the attack speed**.

### Chain drain

| Parameter | Notes |
| --- | --- |
| `ChainMaxFella` / `ChainMaxOsiriNormal` / `ChainMaxOsiriDemand` / `ChainMaxSitNormal` / `ChainMaxSitDemand` | **Five independent caps** (pose × in-mode or not; fellatio has one of its own). 0 = unlimited, **which risks locking up the game** |
| `ChainEcstasyGain` | Whether chain drain accumulates ecstasy |
| `ChainGainPerHp` | **Derived from the effect on HP**, see below |
| `ChainSoftCap` / `ChainWobble` / `ChainWobbleHz` | The soft cap, and the wobble band once it reaches the cap |
| `ChainGainPerDrain` | Fixed-value mode (used when `ChainGainPerHp` is set to 0) |

**"Derived from the effect on HP" is the important part:**

```
增量（占绝顶上限 %） = 本次榨取的伤害 / 最大生命 × 100 × ChainGainPerHp%
```

It uses **the damage constant itself** (`Osiri吸精ダメージ = 5`, `SitKiss吸精ダメージ = 8`, `吸精ダメージ = 7`),
**not the HP actually lost**. With invincibility or an HP lock active, `HPChange` does not actually subtract HP,
so reading the real HP loss gives 0 and chain drain would never rise — while the constant says "how much this
hit was supposed to take off", independent of any survival feature, which is exactly what "the effect on HP" means.

> The fellatio branch's damage is **also scaled by `fellaKyuseiAttRate`**, so that scaling has to be included too.

**Soft cap and wobble**: once it reaches `ChainSoftCap%` (default 60) it stops rising and instead
oscillates sinusoidally between `ChainSoftCap ± ChainWobble` (default 60 ± 20 → **40–80%**).

> **`_demandMode` cannot be used as the test for "the mechanic is active".**
> Riding drain is entered from `Play_SitKiss吸精()` (which forces `kissing` to 2) and **does not set `_demandMode`**.
> If you only look at `_demandMode`, riding chain drain falls into the "normal" bucket
> and is **cut short** by `ChainMaxSitNormal` (default a single digit) — this trap has been hit.

### Return to fellatio and "return accumulation" (Rear)

The end of an ecstasy sequence is a three-way fork:

```csharp
private void Event_OsiriSyaseiOnEnd()
{
    player.Syaseing = false;
    float value = UnityEngine.Random.value;
    if (GameManager.gameover)  Play_Osiri吸精(true);
    else if (value < 0.5f)     Play_OsiriMainMixer();   // 50% 回骑乘位攻击
    else if (value < 0.9f)     Play_Osiri吸精(true);     // 40% 吸精
    else                       tabemi.Osiri解除();       // 10% 【回口交】
}
```

| Parameter | Notes |
| --- | --- |
| `DemandBlockFella` | Cuts out the "return to fellatio" branch while the mode is active |
| `DemandFellaDecay` | The chance of actually returning to fellatio decays as `10% × (1 - decay)^entries` |
| `DemandOsiriBoost` | When it does return to fellatio, lowers `OsiriPenaltyToAppear`, the threshold at which the riding position appears (originally 10/9/8/7 on days 1–4) |

**Return accumulation** (`OsiriReturnEnabled`): after the game goes back from the riding position to fellatio, every
**damage-dealing action** the character performs (attack / ejaculation / absorption) has an `OsiriReturnTrigger%` chance
of raising "the chance of entering the riding position again" by `OsiriReturnGain%`.

- Both the chance and the increment **can wobble** (`OsiriReturnJitter`)
- **At 100% → enters the riding position immediately**
- If the game is about to enter the seated pose at that moment, the seated pose is **suspended** and released once this riding session ends

### Afterglow

Afterglow can be understood as **chain drain with a lower base speed and a longer duration per instance**.

**Accumulation**: it accumulates only **per ejaculation inside Demand / Drain mode**, adding `AfterglowPerSyasei` each time.
Ejaculations outside the mode **do not count**.

**Trigger**: it does not fire immediately. It ignites only once **the last segment and all of its chain drain and similar
activity have finished and the situation is stable** — the condition is "not draining and the mode has ended",
held continuously for `AfterglowSettleDelay` seconds.

> **Gate**: without ever entering Demand / Drain mode, **afterglow will not fire**.
> Looking only at "pending > 0" is not enough — that value survives across cycles.

**During afterglow:**

| Parameter | Notes |
| --- | --- |
| `AfterglowSpeed` | Animation speed (default 70%). **Lowering the speed by itself already lengthens every instance** |
| `AfterglowSpeedWobble` / `AfterglowSpeedHz` | Wobble of the speed itself — afterglow is a "long, drawn-out finish" and should not be a straight line |
| `AfterglowSoftCap` | Soft cap on ecstasy (default 50%), **kept separate from chain drain's 60%** |
| `AfterglowEcstasyWobble` | Wobble amplitude once at the cap (default ±15%, oscillating between 35% and 65%) |
| `AfterglowUrgeScale` | Scaling of urge accumulated from every source during afterglow (default 20%). **Turning it down is what leaves a clean gap after the afterglow** |
| `AfterglowClearsUrge` | When the afterglow burns out, resets urge to zero and drops the gate |
| `AfterglowUseDemandGain` | Whether afterglow keeps accumulating further afterglow during the afterglow (generally should be off) |

**Fellatio / the seated pose will not start before the afterglow has drained** — changing pose mid-way breaks the chain
drain, and the afterglow would then never finish draining.

**Manual afterglow = the survival valve**: `demand afterglow` **force-clears Demand mode**
(mode / segments / timer / urge / chain drain counters all reset to zero).
**Use it when Demand has gone on so long that the pose cannot be changed.**

> While Demand / Drain mode is running, **the seated pose is not allowed to cut in** (there is no timeout; this is by design, not a defect).
> To get out, use the survival valve above.

### Binding kiss (Riding only)

**Riding's chain drain and afterglow only ever happen after entering the binding kiss.**

The reason is hard-coded:

```csharp
public void Play_SitKiss吸精(bool startFrom0)
{
    tabemi.sitState = SitState.kyusei;   // 进榨取
    tabemi.kissing  = 2;                 // ← 同时强制进【束缚之吻】
    ...
```

Its entry condition is `kissing == 2`, reached through
`PrepareKissing()` (`0 → 1`, window `KissPrepareTime`) → `StartKISS()` (`1 → 2`).

In the original this path relies on **a 10% roll or the X key**, and the window does `KissPrepareTime *= 0.9` on every
release — **so it gets shorter the more you play**.

| Parameter | Default | Notes |
| --- | --- | --- |
| `SitKissAutoPrepare` | On | **Enters the binding kiss automatically** (no need to press X) |
| `SitKissAutoInterval` | 6s | Interval between automatic entries |
| `SitKissNoDecay` | On | **Stops the window from shrinking as you play** |
| `SitKissWindowMul` | 200% | Window length multiplier (original 4–5 seconds → 8–10 seconds) |

| Parameter | Default | Notes |
| --- | --- | --- |
| `KissSpeedEnabled` | On | Master switch |
| `KissSpeedMul` | 100% | Kiss animation speed |
| `KissSpeedWobble` | 0% | Wobble amplitude of the speed |
| `KissSpeedHz` | 0.5 | Wobble frequency |

| Stage | Which set applies |
| --- | --- |

```csharp
if (sitState == "kyusei") return;      // 进了榨取 → 交给那套
```

### The Manman zone (a click zone the Riding branch builds itself)

**The model never had a click zone for that part.** The line
`_ = hitAreaUp == "HitArea_Manman";` in the game code is a leftover — search `sharedassets0.assets` and
`HitArea_Manman` **appears zero times** (the only ones present are the five `HitArea_Head` / `Head_Sit` / `Osiri` / `LeftGirl` / `RightGirl`).

**Why it cannot be created in Cubism:**

| Check | Result |
| --- | --- |
| Cubism drawables | **baked into the moc3, cannot be added at runtime** |
| The game's `.cmo3` source project | **does not exist** (only the compiled `.moc3`) |
| Whether Cubism Editor can open `.moc3` | **No** — that is what compiling means |

So the patch **tests a rectangle of its own** and, on a hit, sets the name to `HitArea_Manman` — **a name that does not exist in the game**.

**Why it does not impersonate `HitArea_Head_Sit`**: clicking the head in the seated pose **releases the binding kiss**
(it triggers a skill check when `kissing == 2`); it does not build urge. Impersonating it would make "clicking that area = breaking the kiss", and the features would bleed into each other.

**Manman is a separate path**: the name never reaches the game's `switch`; the patch's own prefix catches it —
accumulating drain urge, running the stacking check, and playing the click effect (reusing the game's own implementation, so it feels the same).

| Part | Function |
| --- | --- |
| **Head** | Releases the binding kiss (the game's original logic, unchanged) |
| **HitArea_Manman** | Accumulates drain urge (handled independently by the patch) |

**Mouse and touch are two separate paths** (this is a trap that has been hit):

| Input | Source of the value |
| --- | --- |
| Mouse | `Live2D_HitAreaCheck.mousePointing` (a static field, computed every frame) |
| Touch | the return value of `GetTouchTargetName(pos)` |

Both have to be hooked; hook only one and the other input method stops working.

**The test is computed from the character model's screen bounding box**, not from screen percentages — it follows the
character and does not drift when the resolution changes.

**Two ways to define it:**

| Method | Notes |
| --- | --- |
| **Asset binding (preferred)** | Give a drawable name and the test area uses **that asset's bounding box** directly. This is real "asset bound to the model": it follows the mesh deformation. The panel lets you **filter and page** through every asset, and clicking a name binds it |
| **Hand-dragged rectangle (fallback)** | The four model-relative ratios `CX/CY/W/H`. With "drag mode" on, the box follows the mouse, and once aligned you click "bind to this position" |

**Visualisation**: with `SitPussyAreaShowRect` on, the box is drawn on screen while seated (unaffected by whether the panel is shown).

### Impact sounds (Riding)

**The rhythm comes from animation events; the tone comes from the speed.**

```
Osiri 骑乘动画片段
    └─ Unity 动画事件（按名字回调 "OsiriSE"）   ← 在资源里，不在代码里
          └─ OsiriSE()
                └─ hSound.PlayOsiri(1..4)   ← 按当前 osiriSpeed 选档
```

**The tiering rule:**

```csharp
if (osiriSpeed < 0.25f)       PlayOsiri(1);
else if (osiriSpeed < 0.5f)   PlayOsiri(2);
else if (osiriSpeed <= 0.75f) PlayOsiri(3);
else if (osiriSpeed <= 1f)    PlayOsiri(4);
```

The four tiers map to four audio groups, `OsiriList1 ~ OsiriList4`.

**Two details worth knowing:**

- **There is overlap protection**: if the previous sound has not reached 80% of its length, this one is dropped outright —
  so impact-sound density has a ceiling, and no matter how fast the animation goes they never pile into a mush
- **The same clip is never played twice in a row**: each tier is a group (several variants), chosen at random but
  **avoiding the one used last time**

**This patch's adjustment** (`OsiriKyuseiTier4`, default on):
**during chain drain it picks at random between tiers 3 and 4; in every other state the original speed tiering is kept.**

> `OsiriSE` is an **animation event** (no caller can be found in code; it appears once, at its definition).
> The ecstasy and absorption stages have their own sounds, `OsiriSyaseiSE()` / `OsiriKyuseiSE()`, and those two
> **do have explicit callers**.

### Implementation traps (worth remembering)

**These methods belong to different classes**, and when a patch is attached to the wrong class Harmony **fails
silently**: one missing "hook applied" line in the log is the same as never having applied it:

| Method | Owning class |
| --- | --- |
| `Osiri叩かれる()` / `UpdateAtt()` / `Osiri解除()` / `頭叩かれるSit()` / `PrepareKissing()` / `KissPrepare解除()` / `DealDamage_Fella()` | **`TabemiControl`** |
| `Event_FellaSyaseiStart()` / `吸精ダメージ` / `OsiriSE()` (on SitOsiri) | **`Live2D_AnimationControl`** |
| `Event_OsiriSyaseiStart()` / `Event_Osiri吸精End()` / `Play_OsiriSyasei()` / `OsiriSE()` / `Even_SitKiss吸精OnEnd()` | **`Live2D_Animation_SitOsiri`** |
| `GetTouchTargetName()` | **`Live2D_HitAreaCheck`** |

> `Sit` and `Osiri` **live in the same class** (the class is named `Live2D_Animation_SitOsiri`); there is no separate Sit class.
>
> This trap was hit **four times in a row**: `Osiri叩かれる`, `Event_OsiriSyaseiStart`, `DealDamage_Fella`,
> `GetTouchTargetName` (`HitAreaCheck` is actually called `Live2D_HitAreaCheck`).
> **After applying patches, always count the log lines.**

**A few more:**

- `Event_Osiri吸精End()` uses a **hard-coded `Random.value < 0.9f`** and never reads `KyuseiRate` at all —
  everything built around `KyuseiRate` has no effect on the riding position whatsoever
- The drain animation's events (`Event_Osiri吸精Damage` / `Event_Fella吸精`) **only call `HPChange`** and

- `_CenterGirl(int)`, which switches pose, is a **delayed coroutine** (`WaitForSeconds` first, then the state change),

### The spank speed impulse (Rear)

Each spank **raises attack speed by a chunk quickly and then lets it fade slowly**; in a streak they stack at a decaying ratio.

| Parameter | Default | Notes |
| --- | --- | --- |
| `SpankSpeedEnabled` | On | Master switch |
| `SpankSpeedGain` | 12% | Size of the impulse on the first spank |
| `SpankSpeedStack` | 60% | Stacking ratio: each new increment = the previous increment × this value |
| `SpankSpeedRise` | 9 | How fast it climbs (fraction of the way to the target per second) |
| `SpankSpeedDecay` | 0.25 | How fast it fades. Smaller fades slower and leaves the effect around longer |

**It is applied to the main mixer animation's playback rate**, not to `osiriSpeed` —
because `osiriSpeed` is clamped by the game to `[0,1]` and `Play_OsiriMainMixer` sets it straight to 1, leaving
**no headroom for a bonus**.

## 4a. A bug the plugin fixes for the game: the DLC path

The original game performs two DLC checks, and **the two paths are inconsistent**:

```csharp
// (1) DLCManager.LoadAssetBundle() —— 正确：游戏根目录
path = Application.dataPath + "/../";
// (2) TitleDLCCheck.InitiateDLC() —— 错误：指向不存在的 Patches\ 目录
path = Application.dataPath + "/..//Patches/";
if (AssetBundle.LoadFromFile(...) == null)
{
    GameManager.DLC = false;
    PlayerPrefs.SetInt("DLC", 0);        // ← 一旦跑到，就把 DLC 永久关掉
}
```

The `Patches\` directory does not exist, so the moment (2) runs it writes the DLC flag as `0`, and the game then falls back to the base atlas (**no clothes**), which shows up as "I picked tights and the legs are bare".

**What the trainer does about it** (it does not modify the game files; it only corrects things once the game has run):

1. Check after `DLCManager.LoadAssetBundle()`: if the bundle loaded, make sure the `DLC` flag is `1`
2. Check after `TitleDLCCheck.Start()`: re-confirm from the **correct path** whether the DLC is present, and correct the flag

The startup log shows:

```
DLC 加载修正补丁已挂载（DLCManager.LoadAssetBundle 后缀）
DLC 加载后检查：包已加载，DLC 标记已是 1
```

If you genuinely do **not** have the DLC files, the plugin respects the original verdict and will not force it on.

## 4a-3. Tights will not display: the real root cause (an index bug in the game itself)

> This section is the **final verdict**. The earlier discussion of DLC and atlases covers necessary conditions, but it is not the reason why "I picked tights and see nothing".

### Symptom

Set **tights = 1 or 2** and the part opacity really does become 1 (visible in the plugin panel), yet there is nothing on the legs.
**You have to "turn forced display of everything on once, then off"**, and only after that do the tights appear normally.

### Root cause

The game's `UpdatePartOpacity()` does contain this line:

```csharp
modelA.Parts[IDs.CenterGirlSitting_Tights].Opacity = _Op_CenterGirlSitting_Tights;
//            ↑ 这个字段是 0
```

`Live2D_IDs.CenterGirlSitting_Tights` **should be 19, but is actually 0** — because `CheckParts()` looks for a child by name under some `parent` level, and under that level there is **nothing** named `CenterGirlSitting_Tights`, so the field keeps its default value `0`.

And **`Parts[0]` is `LeftGirl`**. So every frame the game writes the **left girl's** opacity as 0, and the base tights layer that ought to be lit, **`Parts[19]` (Id = `"Tights"`)**, is never written at all.

`Parts[19]` has **no drawable** of its own — it is a **parent part whose opacity is passed down to its children**. It stays at 0, so:

| Part | Name | With tights selected | Is it the real culprit |
| --- | --- | --- | --- |
| 39 | `CenterGirlSitting_Tights_White` | 1 | only drives the white layer |
| 40 | `CenterGirlSitting_Tights_Black` | 1 | only drives the black layer |
| **19** | **`Tights`** | **always 0** ← | **the base layer; while it is unlit, the two layers above it cannot be drawn** |

### Why "turn force on once, then off" unlocks it

That step calls the plugin's `RestorePartOpacities()`, which writes an **out-of-date part snapshot** back to every part — and **it happens to set `Parts[19]` to 1**, so the tights appear. A lucky hit, nothing more.

(That snapshot write-back was itself a bug and has since been fixed: it now "stops overwriting and lets the game recompute on the next frame", so part opacity is no longer permanently damaged.)

### How the plugin fixes it

After the game has written part opacity (the `UpdatePartOpacity` postfix), it adds the missing line following **the game's own intent**:

```csharp
// 选了裤袜（槽位非 0）就把基础层点亮，否则熄灭
FindPart("Tights").Opacity = (Costume.Tights != 0) ? 1f : 0f;
```

This is **writing, on the game's behalf, the one line the game got wrong**; it is not a way around the game's logic.

### Verification results

| Tights slot | `19:Tights` | `39:White` | `40:Black` | On screen |
| --- | --- | --- | --- | --- |
| 0 (none) | 0 | 0 | 0 | bare legs |
| 1 (black) | **1** | 0 | 1 | black tights |
| 2 (white) | **1** | 1 | 0 | white tights |

### Two detours during the investigation (for reference)

1. **Masks**: we once set the `mask_count` of `ArtMesh186/187/189/190` to 0 directly inside the `moc3` to test this.
   The result: **the masks were fine**. Deleting them only made the tights draw exactly as the mesh authored them, producing the wrong shape.
   (The change has been reverted; the backup is at `model\sharedassets0.assets.moc3backup`.)
2. **`Renderer.isVisible`**: it only reports "did this mesh enter the camera frustum".
   When the legs are out of frame, all 6 tights drawables report `vis=0`, which has **nothing to do with whether rendering is correct**.
   We briefly misread this as "some part is the gate", and only a controlled experiment (moving Tights / Part4 to the end and retesting) ruled it out.

## 4a-2. Activity recorder (a complete record of your actions and resource state)

The 「系统」page → **「[记录] 开始活动记录」** (or press `Ctrl+R` to toggle). When you are done playing, click **「[停止] 停止」**.

Output goes to `BepInEx\l2d_dump\activity_<timestamp>\`:

| File | Contents |
| --- | --- |
| `activity.ndjson` | one event per line, machine-analysable (JSON Lines) |
| `activity.txt` | the same data as a human-readable timeline |
| `summary.txt` | duration, event counts, current state |

### Three kinds of events, aligned on one timeline

| Category | Contents |
| --- | --- |
| **user** | raw keyboard and mouse input (key down/up, mouse clicks, wheel, throttled mouse movement) + clicks on the trainer panel's buttons |
| **game** | the game's response: costume slot changes, HP / ecstasy changes, DLC load and texture replacement, model part opacity changes |
| **sys** | a once-per-second resource sample: FPS, heap memory, texture / material / GameObject / total object counts, current scene |

**Every event carries the game state from that same sample**, so when you read it offline you never have to reassemble the context elsewhere:

```json
{"t":12.34,"cat":"user","kind":"key_down","detail":"R",
 "state":{"cap":1,"tights":2,"opTightsW":1,"hp":100,"ecs":50,"dlc":true},
 "res":{"fps":120,"heapMB":18,"tex":242,"go":867,"scene":"TabemiMain"}}
```

### One key design point: state deduplication

Methods like `UpdateCostume` / `UpdatePartOpacity` / `EcstasyChange` **run on every frame**.
Recorded as-is, a measured 28 seconds produced **1119 noise events**, which completely buried the real actions (**only 14 key presses** in the same window).

So the record points use **state-signature deduplication** — a line is written only when the signature changes:

- costume / parts: recorded only when the slot or the opacity **actually changed**
- numeric values: through **meaningful safety valves** (HP every 5 points, ecstasy every 10%, ejaculation count on every change)

The effect: the size went **from 1.2 MB down to about 50 KB**, and what is left in the timeline is readable state transitions.

### Event coverage

**10 of 11** record points are hooked: `TabemiControl.UpdateCostume` / `RandomCostume`,
`Live2D_ModelControl.UpdatePartOpacity`, `PlayerControl.HPChange` / `HPGaugeChangeValue` /
`EcstasyChange` / `EcstasyGaugeChangePercent`, `DLCManager.LoadAssetBundle` / `SetUpDLCStaffs`,
`TitleControl.UpdatePartOpacity`.

(`PlayerControl.ECstasyReset` is not hooked separately — it is already taken by the change-rate patch.)

## 6. On "uncensoring" (audited; conclusion: this title cannot have switch-based uncensoring)

A full audit was carried out on how this game applies its censorship, and the conclusion is that **there is no mask layer that can be switched off** — the censorship is **drawn into the character art**. So there is no "delete this file / turn off that post-processing step" that reveals the original image. The evidence:

1. **Asset census**: all **292 Texture2D** assets in the game were listed. There is no texture named or functioning as mosaic / censor / mask, and no transparent overlay layer (measured share of near-white opaque pixels: 0.00%).
2. **Code side**: decompiled `Assembly-CSharp.dll` (about 19000 lines) and searched for `mosaic|mozaic|censor|pixelate|blur|修正|モザイク`; it hit only one generic UI blur, `SimpleBlurEffect`, and no censorship-related switch anywhere.
3. **Atlas scan**: the only large Live2D atlas, `texture_00` (8192×8192), was put through mosaic detection
   (edge energy aligned to an 8/16/32 px grid, plus flat-colour block density) — **no quantised blocks, no grid period**, only smooth skin shading.
4. **Quantitative test**: the censorship band in the game was analysed with a "grid mean-colour reconstruction error" test;
   for block sizes 2/3/4/5/6/8/10/12/16 the error was 1.32 / 2.49 / 2.84 / 3.22 / 4.64 / 5.11 / 6.26 / 8.14 / 8.86.
   **It rises monotonically, and no block size shows a local minimum** — a real mosaic would bottom out at the true block size.
   So this is a **continuous gradient (blur / softening)**, and it was applied back at the drawing stage.

The DLC was cleared up along the way: `DLCManager` swaps the replacement atlas onto every part except `ArtMesh207/254/253/15/223/224`,
and the DLC asset bundle holds the complete full-size 8192 atlas (the base atlas occupies only the left half, x 0–4224) — that is an **atlas for costume changes**, not an uncensored version.

**What this means**: the information under the blur does not exist in the source image; it is lossy. The only way to remove it is to let **AI image inpainting** guess the content — the flow is: export `texture_00` → inpaint the censored region → repack the 8192×8192 atlas back into
`sharedassets0.assets` with UnityPy → verify in the game. That **generates content** rather than "lifting the cover"; the result is not guaranteed,
and Live2D deformation may give the edges of the inpainted area away. If you want to do it, treat it as a separate project.

## 6a. Command channel: drive the game from a script (no keyboard, no mouse)

The plugin has a built-in **file command channel**, so that you (or any script / AI) can operate the game **without touching the keyboard or the mouse**.
It does not steal window focus, install no driver, and does not touch system input, which makes it cleaner than `pyautogui` / PostMessage / virtual keyboard-and-mouse schemes.

### Protocol

| Direction | Path |
| --- | --- |
| Write a command | `BepInEx\l2d_dump\cmd\in.txt` (one per line) |
| Read results | `BepInEx\l2d_dump\cmd\out.txt` (appended, with timestamps) |

It polls every 0.1 seconds and clears `in.txt` as soon as the command has run.

### Command table

| Command | Effect |
| --- | --- |
| `ping` | liveness check, replies with the current scene name |
| `scene` / `scene <name>` | read the current scene / switch scene (e.g. `TabemiMain`) |
| `state` | read everything at once: costume slots, `_Op_` fields, opacity of parts 19/39/40, forced state |
| `parts` | **list the opacity of all 44 parts** (which are on, which are off) |
| `tights <0\|1\|2>` | set the tights and apply them |
| `costume <cap\|upper\|lower\|tights\|glasses> <value>` | set a costume slot |
| `force off` / `force all` / `force part <name> on\|off` | forced-display control |
| `click <name or text>` ** `clickobj <name>` | trigger a button / clickable object inside the game (**without going through the system mouse**) |
| `colliders` | list the currently clickable objects (enumerated by callback method) |
| `skipdialog on\|off` | fast-forward dialogue (injected in-game, equivalent to holding Ctrl) |
| `timescale <value>` | set `Time.timeScale` (0 = freeze the picture, handy for stable comparisons) |
| `pix <x0> <y0> <x1> <y1>` | read back screen pixels, **prints numbers only** (mean RGB, share of dark / bright pixels) |
| `rendercheck` | part opacity / `isVisible` of the 6 tights drawables, with a control group |
| `probe <masks\|partindex\|parttable\|atlas\|vmap\|diag>` | trigger the corresponding diagnostic |
| `shot <name>` | screenshot to `cmd\<name>.png` |
| `quit` | quit the game |

### How to use it (three ways, pick one)

> **Prerequisite**: the game must have **started once**, otherwise the plugin has never created `BepInEx\l2d_dump\cmd\`.
> If you get "directory not found / No such file or directory", that is the reason.

#### Way one: bash wrapper (recommended; works from any directory)

```bash

bash /e/DSH/build/burger-shop/tools/gcmd.sh states
bash /e/DSH/build/burger-shop/tools/gcmd.sh            # 不加参数 = 显示全部命令用法
```

**Do not use a relative path** (`tools/gcmd.sh ...`) — that depends on which directory you are in, and from `~` it will always fail.
**The arguments do not need quoting either**: `tremor fire` and `"tremor fire"` both work.

#### Way two: PowerShell / cmd wrapper

```powershell

<repo>\tools\g.cmd states
```

The script itself **contains no Chinese**; the game path is read from `gamepath.txt` in the same directory as UTF-8 — so the cmd / PowerShell code page cannot affect it.
(The `.ps1` is saved as **UTF-8 with BOM**; otherwise PowerShell 5.1 reads it as ANSI, and the bytes in the Chinese comments get taken for quote characters, which ends in a syntax error.)

#### Way three: read and write the files directly (no script at all)

```bash

```

**The protocol is just these two lines**:

| Direction | Path | Notes |
| --- | --- | --- |
| Write a command | `BepInEx\l2d_dump\cmd\in.txt` | one per line, **must be UTF-8** (no BOM) |
| Read results | `BepInEx\l2d_dump\cmd\out.txt` | appended, with timestamps |

The plugin polls every 0.1 seconds and clears `in.txt` immediately after executing. So **one file cannot hold two commands that have to run in order** —
if you need a gap, write them in two separate steps.

for reaching a testable state unattended.

### Why it is worth using this to decide "did it render"

**When anything on screen is moving, screenshot comparison is unreliable** — the difference contains the target object, the animation and the camera all at once,
and the three cannot be separated. So deciding "did something get drawn" has to follow this priority:

1. **Read the game state** (part opacity, field values) — independent of the picture, always reliable
2. **Read the renderer's effective state** — equally independent of the picture
3. Controlled differential (freeze with `timescale 0` first, then compare)
4. Pixels — the last resort, and **print numbers only**; do not judge by eye

On this project, because there was no state-reading channel at the start, we could only infer from screenshots, and drew the wrong conclusion
again and again (taking the ecstasy white flash for white tights, taking camera movement for a costume change taking effect).

## 7. Technical notes

- **Engine**: Unity 2022.1.24f1, Mono backend (there is `MonoBleedingEdge`, and `Assembly-CSharp.dll`
  is a managed assembly, not IL2CPP). That is what makes the BepInEx 5 route work.
- **Approach**: the plugin does not reference `Assembly-CSharp.dll`; it finds types by reflection, by name —
  `ProgressHub` / `PlayerControl` / `TabemiControl` / `ClockControl` / `Live2D_AnimationControl`
  and so on — caches the `FieldInfo` and then reads and writes them directly. The benefit is that a game update to a new version is unlikely to break it.
- **Access chain**: `ProgressHub` exposes the common objects as static references (`ani` / `tabemi` / `clock` / `menu`),
  and the plugin reads those first; `PlayerControl` is reached through `Live2D_AnimationControl.player`.
  (`ProgressHub` itself has no `player` field — this is easy to misread.)
- **Which field lives where** (pits we fell into, written down so nobody has to look again):
  - `fellaSpeedPlus` is in `Live2D_AnimationControl`, **not** in `TabemiControl`
  - `sitSpeedPlus` is in `Live2D_Animation_SitOsiri`
  - `ateCount` is a **property** of `PlayerControl` (backing field `_combo`), not a field
  - `Chapter1` / `Chapter2` inherit from `ProgressHub`, so `FindObjectOfType` on the base class does not catch the derived class;
    the plugin uses the static reference as its main path
- **Font / DPI**: the editor carries a PerMonitorV2 DPI-aware manifest, and the layout is multiplied explicitly by `DeviceDpi`,
  so on a high-DPI screen it renders natively sharp instead of being bitmap-stretched by the system.

### Burger-making countdown

After an order you have a limited time to make the burger, and running out of time counts as a failure. This countdown can be adjusted.

| Parameter | Default | Notes |
| --- | --- | --- |
| `BurgerTimeAll` | 0 | time to make each order (seconds). 0 = use the game's original (10 seconds) |
| `BurgerTimeSpeed` | 100 | countdown speed (%). 100 = original speed; 50 = half speed; 0 = frozen |

Once **frozen (0)** the countdown does not run and you can take your time.

The panel is at the bottom of the 「玩家」tab and has three shortcuts: 「原版」(10 seconds / normal speed), 「冻结倒计时」(freeze the countdown), 「宽松」(30 seconds / half speed).

Command line: `set BurgerTimeAll 30`, `set BurgerTimeSpeed 50`

**Implementation note**: the game **decrements first and tests for zero afterwards**,
so the patch hooks the **prefix** of `MenuControl.Timing` — it adds the time that should be added first,
then the game subtracts `dt`, so the net value equals `dt × speed`, and the zero test also sees the compensated value.

If it hooked the postfix instead, the zero test would already have run and the timeout would already have fired, and freezing and slow speed would have had no effect at all.

## 8. Directory layout (source)

```
<repo>\
├── plugin\       BurgerShopModder.cs / .csproj     ← 游戏内插件的源码
├── trainer\      BurgerShopTrainer.cs / .csproj    ← 外部编辑器源码
├── installer\    Installer.cs / payload.zip        ← 安装程序源码与内嵌载荷
├── verify\       Verify.cs / .csproj               ← 反射字段校验器
├── src\          Assembly-CSharp.decompiled.cs     ← 反编译出来的游戏逻辑（参考）
├── refs\         编译用的引用程序集副本
└── dist\         编译产物
```

Rebuilding (the order matters: the payload has to be rebuilt first, because the installer embeds `payload.zip` into the exe):

```powershell
cd <repo>\plugin    ; dotnet build -c Release
cd <repo>\trainer   ; dotnet build -c Release
cd <repo>\installer ; pwsh -File make_payload.ps1
                                        dotnet build -c Release
```

Checking that every reflection path matches the game's actual DLL:

```powershell
<repo>\verify\bin\verify.exe "<游戏>\Four Nights at the Burger Shop_Data\Managed"
```

Only when everything reports `OK` is the trainer usable — this verifier has caught three wrong field owners, so running it once first is recommended after a game version change.
